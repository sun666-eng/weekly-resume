# 给 GLM 的系统性简历一致性审查提示词

请在 `D:\MyProjects\Weekly  Resume\weekly-resume-release` 中执行本次审查。注意 `Weekly` 与 `Resume` 之间有两个空格。你负责独立复核，不要把前一个 Agent 的报告当作通过证据。

## 1. 目标与范围

围绕这条主线找出真实缺陷并完成最小修复：

**原始简历 → 导入 → 编辑字段 → 内存数据 → 保存接口 → 数据库 → 刷新回读 → 模板预览 → PDF / DOCX / Markdown / JSON → JSON 回导 → 公开分享。**

重点排查：层级丢失、字段错位、内容被截断或静默丢弃、隐藏字段泄露、模板切换改写数据、编辑器有值但成品无值、不同导出格式内容不一致。完成后交付可重跑证据与 Markdown 报告，供 Codex 审核。

本轮以本地环境为准。不要提交、推送、部署或修改线上数据库。不要修改真实用户简历来做破坏性测试。使用独立测试账号及专用样例。

## 2. 工作约束

1. 先读根目录 `AGENTS.md`、`CONTEXT-MAP.md` 与相关包说明，按要求检查本地 skills。
2. 执行 `git status --short`，记录起始分支、HEAD、未提交文件。工作区已有多位作者的大量修改，不得 reset、checkout、clean 或回退他人文件。
3. 本地运行使用 `compose.nightly.yml`、`.env.nightly`，页面端口 3100，Mailpit 8025。不得删除数据卷、清空数据库、打印密钥、密码或真实用户数据。若启动方式发生变化，先检查实际环境。
4. 复用现有表单、按钮与布局风格，不做视觉重设计，不为方便测试重构无关功能。
5. 不以屏蔽校验、调低阈值、跳过测试、删断言、改快照来制造通过。超时要区分环境资源与代码故障，记录首轮失败和重跑命令。
6. 不并行运行生产构建、全量 PDF 渲染和全量 web 测试。遵循包内 Vitest 配置，PDF 渲染冷启动可能较慢，不盲目扩大 worker 数。
7. 不把 mock 模型通过写成真实 LLM 通过；未连接真实模型时，明确标记未验证。不要使用找到的真实 API Key 自动产生付费请求。
8. 未识别的简历内容不得凭空编造，也不得以“解析成功”为名静默丢弃。需要策略选择的地方，给出保留原文和可撤销的方案。

## 3. 已知背景，需要独立复核

之前专业技能被导入为同一级条目：分类“硬件与通信”和“MQTT”等成员都成了 `skills.items[].name`，模板因此逐条加粗、占满两页。现有数据结构实际支持 `name` 分类 + `keywords[]` 成员，无需数据库迁移。

本次修复涉及：

- `packages/import/src/skill-lines.ts`：识别明确分类与后续技能列表。
- `packages/import/src/plain-text.ts`：接入分组；防止部分大写技能误识别为新章节；补充“个人评价”别名。
- `packages/resume/src/skill-groups.ts`：显式合并普通技能条目；共享批量文本分隔逻辑。
- `apps/web/src/features/resume/builder/skill-group-organizer.tsx`：用户选中条目、指定标题、预览、合并、撤销；阻止过期操作覆盖较新编辑。
- `apps/web/src/routes/builder/$resumeId/-sidebar/left/sections/skills.tsx`：展示关键词摘要。
- `apps/web/src/dialogs/resume/sections/skill.tsx`：中文分类名称、具体技能、可折叠评分设置。
- `apps/web/src/components/input/chip-input.tsx`：技能表单开启批量粘贴及失焦提交；输入法组合输入保护。
- `packages/ai/src/prompts/parser-system.md` 与技能 schema 描述：强调保持原始分组。
- 中文、繁体中文、英文目录已补本轮文案。

先阅读 `docs/skill-group-fix-review-2026-09-26.md`（若已生成），再独立运行相关测试。上述事实不能替代你自己的复现。

## 4. 第一阶段：画出字段流向，先找相同类型问题

建立字段映射表，每一行至少记录：

`章节 / UI 标签 / schema 路径 / 导入写入点 / 编辑写入点 / 保存与回读 / PDF / DOCX / Markdown / 无障碍文本 / 隐藏条件 / 测试证据`。

必须覆盖：

| 范围 | 重点 |
|---|---|
| 基本信息 | 姓名、电话、邮箱、求职意向、性别、年龄、政治面貌、住址、博客、GitHub、自定义字段、头像 |
| 教育背景 | 学校、学历、专业、学校层级、时间、成绩、课程、描述 |
| 工作与实习 | 公司、部门、岗位、工作类型、地点、时间、描述、多岗位；实习能否独立保存 |
| 校园经历 | 是否误入工作/志愿章节；自定义 experience 章节在所有导出中是否保留 |
| 项目经历 | 项目名称、角色、时间、链接、技术栈、职责与成果 |
| 专业技能 | 分类、成员、长描述、评分、列表/连续布局、多列、隐藏、旧的平级条目 |
| 获奖与证书 | 名称、授予单位、日期、链接、描述，不能互换 |
| 科研成果 | 标题、作者/发布者、日期、链接、描述 |
| 个人评价 | 富文本、列表、链接；“个人评价/自我评价/总结”等别名 |
| 其他与自定义 | 语言、兴趣、社交资料、推荐人、志愿经历、自定义章节类型和 ID |

已独立确认一个本轮技能修复范围外的问题，请优先修复：

输入 `测试用户\n\n个人信息\n邮箱：fixture@example.com\n电话：13800000000\n\n教育背景\n示例大学` 后，`basics.email`、`basics.phone` 为空，联系方式落入 `summary.content`。实测结果见 `output/playwright/skill-groups/contact-probe-result.json`，复现脚本同目录 `contact-probe.mts`。期望：联系方式正确映射到基本信息；未知个人资料保留，不能丢弃或覆盖已有明确字段。请覆盖“姓名在章节内/章节外、个人信息/个人资料别名、字段同行/分行、重复与冲突联系方式、无联系方式章节”等边界，独立复现后修复。

其他可疑路径，先复现再定级：

- 普通文本的“个人信息/个人资料/求职意向”别名目前如何映射，会不会把联系方式收进 summary。
- 普通文本“实习经历/校园经历”是否与中文空白简历的独立章节约定一致，能否表达原始分类。
- `splitList` 等通用分隔函数是否把描述中的逗号、斜杠、连字符当作新条目；是否存在静默去重或数量截断。
- 全大写技能、英文标题、空行、冒号、列表符号是否被误识别为新章节。
- ChipInput 在其他章节是否同样存在未确认输入丢失；它们是否启用 `commitOnBlur`，现有提示是否足够清晰。
- 同名关键词在导入、React key、拖动编辑和再次保存时是否被错误合并。
- 隐藏章节、隐藏项目和自定义字段的过滤是否在所有导出及无障碍文本中一致。

这些是审查线索，不是已经证实的所有缺陷。不得把推测写成确认问题。

## 5. 第二阶段：对抗性数据矩阵

至少建立以下完全虚构的可复用样例，为每个字段放置可唯一检索的标记，例如 `EDU-A17`、`PROJECT-B29`。不能只检查“文件能生成”。

1. 中文空白简历，从零填写全部章节；姓名用两个汉字。
2. 中英文混排，保留 `C++`、`C#`、`.NET`、`Node.js`、`NB-IoT`、`ESP32-C6`、`Netty/MQTT`、`Linux/Windows`。
3. 三组技能各六项：分类+逗号列表、分类+逐行成员、冒号分类、项目符号列表；中文/英文分隔符及括号内逗号。
4. 无分组技能：不能凭空推断分类；一项技能、空分类、70 项以上技能、重复名称、超长描述。
5. 技能已有熟练程度、图标、评分、关键词、隐藏状态：批量合并不得丢失这些属性或意外公开隐藏内容。
6. 专业技能与下一章节相邻；下一章节使用“个人评价/自我评价/教育背景/WORK EXPERIENCE”等实际标题。
7. 长简历至少 3 页；长中文、长 URL、英文长词、emoji、特殊符号、多层列表和空段落。
8. 旧版 JSON、当前 JSON、JSON Resume、无关键词数组、缺少新增字段、未知字段、异常字段类型。
9. 仅一项或全部为空；删除最后一项后不留下空标题或巨大空白。
10. 性别“不公开”、隐藏联系字段、隐藏整个章节：所有成品与匿名页不得泄露。
11. 在编辑输入框中输入但不按回车，直接保存；Tab 离开、点击取消、切换章节；中文输入法候选确认不得误提交。
12. 断网、保存失败、刷新、登录失效、两个标签页同时改不同字段、同字段冲突、合并预览后另一标签编辑、撤销前已有新修改。

每个失败样例保存最小复现输入，固定原始文本和预期结构。不要使用真实用户的联系方式或经历作为测试夹具。

## 6. 第三阶段：真实浏览器与导出核验

### 6.1 编辑与持久化

- 从零创建和文件导入两条路径分别测试。
- 每次保存后刷新，必要时退出再登录；比对字段内容与顺序。
- 新建、编辑、排序、隐藏、删除、移动到自定义章节、撤销；正确处理空值。
- 切换至少三种布局差异明显的模板，并对项目里全部模板做数据不变性检查。
- 测试 390px 宽度、键盘操作、滚动与模态窗口，不得让必需操作超出屏幕不可点击。

### 6.2 技能修复必须额外测试

- 实际上传 PDF 后只产生预期分组，而不是只直接调用 parser 单元函数。
- 合并前预览不写数据；选中条目顺序和原始顺序有差异时仍保持原始顺序。
- 标题可以是选中条目之一；未选标题、只选一个、选中后条目被删除必须安全失败。
- 合并后撤销恢复完整数据；出现较新修改后，不能用旧快照覆盖它。
- 切换不同简历后，不能带入上一份简历的选择或撤销快照。
- 刷新后恢复的是已经保存的分组；不要把“本页即时撤销”当作长期版本备份功能。
- 关键词保持普通正文，分类加粗；长组合理换行，分页不漏字、不重字，模板渲染不修改数据。

### 6.3 成品与回导

- PDF：提取实际生成的 PDF 文本并对照所有标记；逐页渲染成图片检查裁切、遮挡、空白页、跨页标题和左右边界。
- DOCX：解包核查文本与层级，有条件使用实际办公软件渲染；无法渲染则明确写“仅 XML 内容核验”。
- Markdown：核对文本、链接、分组与列表；不能用去掉全部标点后的字符串比较掩盖结构错误。
- JSON：导出后重导入，比较规范化后的数据；只排除确实重新生成的标识，不随意忽略丢失字段。
- 公开分享：使用匿名上下文，验证公开版与编辑预览内容一致；关闭分享后不可访问；不要公开含真实隐私的样例。
- 离线字体：阻断 Google 字体域名后冷启动和导出，记录实际网络请求；不要把浏览器缓存命中误当本地字体完整。

## 7. 第四阶段：修复与回归规则

1. 每个问题写清：编号、严重级别、用户操作、最小样例、预期、实际、根因文件和行号、影响路径。
2. 修复放在正确的包；纯简历行为进 `packages/resume`，解析进 `packages/import`，字段约束进 schema，工作流进 web，PDF/DOCX 各自处理。
3. 优先复用现有字段。新增 schema 前先说明旧数据、JSON、API、Agent、全部导出的兼容策略。
4. 已保存数据的自动迁移必须保守、可备份、可回滚；不能仅凭中文标签猜测后批量改写真实简历。
5. 先让最小回归测试失败，再实施修复，记录前后结果；后续应运行受影响包的完整测试、类型检查、边界检查和生产构建。
6. 付费模型未测、浏览器未测、扫描件 OCR 不支持、生产环境未测等必须单独列出，不能被“全绿”掩盖。
7. 遇到未知大改先写方案，不把系统性审查扩大成新功能开发。
