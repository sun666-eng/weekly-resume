无法演练时提交明确步骤和未验证项，不修改部署脚本来让检查通过。

## 六、独立测试补充的质量要求

每个新增测试必须回答“它能发现哪一种现有测试可能漏掉的错误”。

- 预期值来自虚构样例规范、产品声明或经确认的行为契约，不能照抄当前输出当正确答案。
- 测试检查用户可见行为或数据不变量，避免只 grep 源码字符串、验证自己写的 mock。
- Mock 只替代网络、时钟等边界；不要把被审查逻辑也 mock 掉。
- 时序测试使用明确的延迟控制或挂钩，避免靠盲目 sleep 碰运气。
- 不删断言、不提高所有超时、不关闭隔离来掩盖失败。
- 偶发失败保留首个日志和复跑结果；单独复跑通过只能说明可能不稳定，不能抹去失败。
- 区分单元、集成、浏览器、真实导出和人工验收，不能把同一测试重复计数。
- 每份补充测试写明目标文件、依赖、命令、环境、是否执行、预计捕获的缺陷；不改原测试目录。
- 如果接口是私有函数，优先通过公开行为测试；若必须使用隔离探针，解释与真实调用路径的差异。
- 有条件时在独立测试副本内做受控故障替身验证测试敏感性，不修改原项目，也不把替身故障当产品真实缺陷。

## 七、发现分类与反证门槛

每条记录必须属于以下一类：

| 分类 | 要求 |
| --- | --- |
| 已实际复现 | 有确切基线、可重跑步骤、实际输出和明确违背的预期 |
| 静态证据支持，未运行 | 有调用链和保护条件分析，明确尚未复现 |
| 待确认 | 存在疑点但证据不足，不能计入确认缺陷 |
| 已知限制/产品取舍 | 已有声明或明确策略，说明用户影响，不当作新缺陷 |
| 环境或测试工具问题 | 例如 Docker 中断、浏览器上传接口卡顿，不能直接归因业务代码 |
| 已撤回 | 保留原判断、反证和撤回原因，不删除历史记录 |

对每个拟报缺陷，必须主动寻找反证：

1. 上游鉴权、schema、状态机、取消机制或版本检查是否已经保护？
2. 当前依赖精确版本的行为是否与推断一致？不要用另一个版本文档代替安装源码。
3. 路径真实可达吗，还是需要不存在的前置状态？
4. 后端数据是否真的改变，还是预览、缓存、异步等待或测试工具造成的暂态？
5. 是否把回退失败但数据未变，误写成数据被覆盖？
6. 是否已被历史修订撤回，或已被当前代码修复？

优先级和证据置信度分开：

- P0：已证实的严重跨账号泄漏、广泛不可恢复数据破坏等，需给出完整证据链。
- P1：核心流程被阻断、明确数据丢失/错误覆盖、重要权限问题。
- P2：有恢复路径或变通方式的功能问题、范围受限的一致性缺陷。
- P3：小范围文案、视觉和非阻断体验问题。

未复现的高影响风险可以写“潜在高影响”，不能凑成“已确认 P0”。发现严重问题时停止扩大影响范围，保存最小证据即可。

output/grok-independent-audit/<run-id>/

### audit-report.md

包含：结论、审查范围、版本身份、确认问题、待确认风险、已知限制、覆盖缺口、是否足以继续本地验收。
不要给未经验证的发布放行；各状态分别计数。

### findings.md：每条发现使用固定字段

```text
ID：例如 PHOTO-001
标题：具体触发条件 + 错误结果
分类：已实际复现 / 静态未运行 / 待确认 / 已知限制 / 环境问题 / 已撤回
优先级与置信度：分别说明
基线：HEAD + 工作区源码哈希/快照 + 镜像
入口与前置条件：账号权限、简历状态、模板、网络条件
预期依据：产品声明、UI 说明或数据不变量
最小复现：编号步骤，提供虚构样例路径
预期结果：可判断的输出
实际结果：实测原始结果，注明等待条件
证据：截图、脱敏请求结果、JSON 差异、导出文件、日志
源码位置：实际路径与当前行号；解释调用链
反证检查：检查过的保护机制及为什么仍成立
影响范围：哪些输入/模板/用户会受到影响
修复方向：文字建议，不实施修改
建议回归：修复后必须通过的断言
未确定事项：不能证实的部分
```

### test-report.md 与 coverage-matrix.csv

每个用例记录：

```text
case_id,module,scenario,priority,test_level,baseline_id,environment,
fixture,expected,actual,status,evidence,finding_id,not_run_reason
```

状态仅使用 `PASS / FAIL / BLOCKED / NOT_RUN / NOT_APPLICABLE`。
补充命令、开始/结束时间、耗时、退出码、失败次数、复跑结果和日志位置。
不要在 CSV 或日志写认证头、cookie、凭据或真实个人信息。

### missing-test-cases.md

按价值排序列出尚未执行/建议长期纳入的测试。每条包含风险、为何已有测试不足、测试层级、准备工作和预期断言。
已执行并通过的用例不要再伪装成测试缺口。

### codex-review-handoff.md

让 Codex 能够不重新遍历整份项目就开始复核：

1. 首先复现的最多 5 个问题，以及原因。
2. 每个问题的确切文件、测试/样例、执行命令与证据路径。
3. 原项目是否被改变；审查前后哈希范围、差异及可能的并行改动。
4. 哪些发现存在争议、反证或环境依赖。
5. 补充测试建议放到哪里，哪些需要 Codex 调整后才能进入项目。
6. 专属本地服务、端口、数据库/卷名称及停止方式；凭据只说明安全的本地存放位置，不给值。
7. 未完成事项、阻塞原因、下一步最小操作。
8. 明确声明：没有修复业务代码，没有提交/推送/部署。

### artifact-manifest.json

记录报告与证据的相对路径、SHA-256、大小、用途和对应 case/finding ID。
忽略清单文件自身，避免递归哈希。报告里引用的证据必须真实存在；不存在的不能用占位符冒充。

## 九、结束前自查

- 有没有把旧报告中的通过结果写成本轮执行？
- 有没有把静态推演、mock 成功、复跑成功或 UI 截图当作完整流程证明？
- 有没有忽略未提交/未跟踪文件，测试了另一个版本？
- 有没有把工具等待或环境故障归因于产品？
- 有没有没有反证检查就报高危？
- 有没有记录 DOCX 无照片等已知限制，避免重复报新缺陷？
- 有没有覆盖一项结论所需要的全部前置条件，而不仅是最后一个按钮？
- 有没有在原业务目录或共享环境做了未授权的修改？
- 关键报告、用例、日志、截图、导出文件和哈希是否能对应？

最后只向用户汇报：本轮基线、已完成模块、实际测试结果、按分类计数的发现、最重要的最多 5 条、未验证项、交接文件路径及操作边界遵守情况。

**现在开始建立基线，按顺序执行。把修复工作留给 Codex。**
