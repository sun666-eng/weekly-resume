## 4. 任务一：撤销、重做和 Agent 回退

### 产品目标

编辑器顶部固定展示“撤销、重做、历史版本”；Agent 修改结果默认展示“查看修改前后、撤销本次修改”，撤销后可以重新应用。较早记录的整段恢复必须与撤销单次修改明确区分。

“一步”应是一次有意义的操作：连续修改同一字段可合并，不同字段不因操作间隔短而混为一步；模板及配套布局变化作为整体；照片与显示设置作为整体；一次 Agent 请求可能包含多个工具调用，需要明确分组边界。

核心要求：撤销 Agent 的项目描述修改时，应保留用户后来修改的电话；同一字段存在后续修改时，应暴露冲突而非静默覆盖。

### 优先阅读位置（若路径改变则自行定位）

- `apps/web/src/features/resume/builder/draft.ts` 及 draft、merge、draft-recovery 相关实现和测试。
- `apps/web/src/routes/builder/$resumeId/-components/dock.tsx`
- `apps/web/src/routes/builder/$resumeId/-components/header.tsx`
- `apps/web/src/routes/builder/$resumeId/-components/version-history.tsx`
- 各字段表单、富文本输入、章节弹窗和技能分组整理器。
- `apps/web/src/routes/agent/-components/agent-chat.tsx`
- `apps/web/src/routes/agent/-components/patch-approval-card.tsx`
- `packages/api/src/features/agent/actions.ts`、`service.ts`、`runs.ts`
- `packages/api/src/features/resume/` 下保存、patch、版本恢复和事件实现。
- Agent action 与简历版本数据库结构；共享 patch、merge 实现。

### 必查问题

1. 所有编辑入口是否经过同一历史记录机制？遗漏的直接写库路径有哪些？
2. 表单内尚未提交的值、失焦保存、自动保存防抖、已在途请求与撤销的先后顺序是否正确？画出具体时序。
3. 是否存在“撤销成功后，晚返回的保存响应又覆盖回来”？失败重试和服务端事件是否能导致同类问题？
4. 当前 500ms 合并是否跨字段、跨章节、跨操作类型？无实际变化是否浪费历史步数？
5. 输入框和富文本原生 Ctrl/Cmd+Z 与整份简历撤销如何分工？中文 IME 组合输入、弹窗和快捷键是否冲突？
6. 撤销后继续编辑是否清空重做分支？快速连续撤销/重做、到达历史上限、切换简历和账号是否隔离？
7. 外部标签页、Agent、版本恢复引起的状态更新如何处理本地历史？不能用整文档快照覆盖他人的新字段。
8. Agent 回退是逆向修改还是整文档恢复？检查 expectedUpdatedAt 等版本条件是否在实际写入时原子校验。
9. 一次 Agent 请求多个 patch 如何分组？部分失败、取消、任务仍运行时撤销如何定义？跨会话修改同一简历如何处理？
10. 连续撤销两个 Agent 操作时，版本时间与 action 状态是否仍能正确衔接？撤销后再应用需要哪些额外记录？
11. 经历删除、增加、排序后，逆操作是否按稳定 ID 对齐？数组索引漂移会不会修改错误条目？
12. 回退失败后 action 被标记 conflicted 是否导致永久无法重试？重复请求是否幂等？
13. 版本恢复是否先保留当前数据？恢复请求与自动保存、另一标签页保存之间是否有覆盖风险？
14. 记录快照只包括 ResumeData 还是也包括文件名、标签、公开状态？明确范围，不建议把权限和账号设置纳入普通内容撤销。
15. 草稿恢复、当前会话撤销与持久化历史版本的职责是否重叠或冲突？历史数据保留与删除是否合理？
16. Agent 撤销后，模型上下文与预览是否刷新？模型是否可能继续按旧数组位置修改？

交付方案：优先复用现有机制；分别给出最小第一期、必要数据结构/API 变更、后续增强。不要只写“使用历史栈”；需要状态迁移、事务边界、冲突规则和可执行验收标准。

## 5. 任务二：照片完整链路

从以下顺序追踪真实函数调用、输入输出和失败处理：

选择文件 → 文件校验/处理 → 上传请求 → 存储写入 → 返回地址 → 写入表单 → 保存简历 → 服务端回读 → 编辑器缩略图 → 模板预览 → PDF/DOCX → 公开分享 → 刷新/重登。

优先定位：编辑器 picture.tsx、上传 API、storage service、静态 uploads 路由、picture-url 工具、PDF browser/server 适配器、模板照片组件、DOCX 图片处理，以及相应测试。

必查：

- 上传成功与简历保存成功是否被混为一谈；表单异步状态是否可能保存旧 URL。
- 连续上传 A/B 且 A 晚完成、上传中删除照片、上传中离开页面、失败后重试时，最终地址归属是否正确。
- localhost、127.0.0.1、不同端口、容器地址、反向代理路径、HTTPS、相对路径与外部 URL 的处理是否一致。
- 地址标准化是否误改合法第三方地址，或造成不可信地址访问、跨用户资源访问等风险。只做静态分析。
- 浏览器可访问的地址是否也能被服务端 PDF/DOCX 渲染器访问；带鉴权照片在公开页的行为是否符合产品设计。
- 本地存储、S3、图片处理开关各条分支是否一致；PNG/JPEG/WebP/透明图/损坏文件/不支持格式有无明确反馈。
- 上传状态、隐藏开关、照片尺寸、裁剪、旋转、模板是否支持照片，能否区分“未渲染”和“资源加载失败”。
- 图片缓存、内容类型、资源持久化和删除策略是否使刷新或重建后图片消失。
- 替换/删除照片后原文件是否仍可用于撤销和历史恢复；清理机制是否可能提前删除仍被历史引用的资源。
- 所有模板是否使用一致照片入口；首页缩略图正常不能证明用户照片正常。

输出逐段链路表：代码位置、数据形式、调用方、校验、失败反馈、测试覆盖。对已知故障列出多个可能根因及如何区分，不要仅凭 localhost 字样或截图断言根因。

## 6. 任务三：测试遗漏与后续验收清单

以本轮两条主链路为重点，补充检查注册登录/会话失效、中文空白简历、导入、自动保存、模板切换、四格式导出、公开分享和账号隔离与它们的交叉影响。

建立矩阵：场景 ID、前置数据、步骤、预期、现有测试文件、覆盖层级、缺口、建议执行环境、优先级。

必须区分：

- 单元测试只验证函数输出，不等于浏览器成功。
- mock API/LLM 不等于真实网络/真实模型通过。
- DOM 中存在 img 不等于图片加载，需 naturalWidth > 0 或等价检查。
- 返回 200 不等于导出内容正确，需正文、图片、分页与隐藏字段验证。
- 界面显示“已保存”不等于持久化，应刷新或新会话读回核对。
- 多标签页轮流编辑不等于真实并发，需明确控制请求顺序。
- 测试通过不证明未测试的同类入口正确。

至少提供这些后续用例：

1. 自动保存请求在途时撤销，延迟响应返回后刷新，状态仍正确。
2. 手动改电话 → Agent 改项目 → 手动改邮箱 → 撤销 Agent，仅项目恢复。
3. 两方改同一项目字段，撤销明确报告冲突且不丢数据。
4. 拖拽排序/删除经历后回退，不把内容写入其他条目。
5. 上传 A、再上传 B，A 晚完成；界面、存储、导出一致指向 B。
6. 照片替换后撤销，旧照片仍可加载；刷新与导出结果一致。
7. 切模板/照片隐藏/撤销/重做交替操作，表单、预览、导出一致。
8. 会话过期/断网中撤销后重新登录恢复，不被旧自动保存覆盖。
9. 同一字段中文 IME 输入和撤销，文本不重复、不截断。
10. 公开关闭后匿名无法读取私有简历；审核图片访问策略是否符合约定。

可以在 Markdown 里写测试伪代码或建议测试名，不新增可执行测试、不更改现有断言来掩盖失败。

- 类型：现有缺陷 / 设计缺口 / 测试缺口 / 待验证疑点。
